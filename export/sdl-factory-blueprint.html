SDL Factory Blueprint

A software factory: deterministic Python workflows drive coding agents through plan → build → test → review → document, with a human at exactly two gates. This document carries every contract you need to rebuild it — the orchestration core, the model roster, the queue, the merge machinery — and marks precisely which parts are harness-specific so you can swap in your own.

01The idea

One sentence governs every design decision: agent proposes, code disposes.

Deterministic Python owns sequencing, retries, and acceptance. Coding agents are bounded nodes inside named phases — they never decide what happens next. Every agent hands back a typed JSON envelope; code verifies every claim in it against the actual filesystem and git state before accepting it. Everything streams to SQLite. The core pattern is disler's Super Simple Software Factory (MIT), kept untouched; this project adds a Kanban queue, an always-on engine, worktree parallelism, and an integration-branch merge gate.

A human appears at exactly two moments, never in the middle:

  • Gate 1 — ratify. The plan (decision ledger, feature inventory, cards) is approved before any code exists.
  • Gate 2 — merge. A finished, integrated chunk lands on main only by the operator's own squash-merge click. Nothing in the factory ever merges to main or pushes it.

The daily loop, compressed: documentation-factory ingests everything once, builds the decision ledger the operator ratifies (Gate 1), and emits the feature inventory — scoped, ordered, dependencies declared → /to-kanban batch-publishes the inventory as queue cards, one per feature, with Needs: edges carrying the blocking order (a git push is the whole handoff) → the engine dispatches each ready card on its own branch and worktree → it integrates autonomously after deterministic checks → a morning brief narrates each run → the operator's click ships the chunk. These two supply-line skills are the factory's own; they replaced the earlier spec→tickets→triage chain.

02The core: one agent call, fully verified

Everything lives in adws/adw_modules/ (~17 modules). The unit of composition is the phase; the unit of trust is the envelope; the unit of proof is the gate.

2.1 The phase model

An ADW is a plain Python script that opens phases through one primitive, run.phase(PhaseParams(...)) — a context manager (runner.py:135). Any exception marks the phase failed and closes the trace; a clean exit marks success. Status defaults to fail: success must be earned.

Phase kindOwnerWhat runs
engineerthe human's nameCaptures the request into the trace. No execution.
agenta roster agent nameph.call(AgentCall(...)) → one verified agent invocation (below).
codegit / qualityDeterministic Python: worktree cut, git commit, diff capture, lint/typecheck/test/scan.

Every PhaseParams requires a description that a Pydantic validator rejects if blank or if it merely restates the name (data_types.py:32) — it is the one sentence the trace and console ever show about intent. Phase ids are {adw_id}_{seq:02d}_{name}; a rejoined run continues the sequence counter instead of colliding.

2.3 The envelope contract

Every agent's final message must be JSON parsing into an EnvelopeBase subclass (data_types.py). Extraction is deliberately permissive: first fenced ```json``` block, else the outermost {...}. Base fields on every envelope: status: "success"|"fail", summary, artifacts: [], notes_for_next_agent.

EnvelopeExtra fieldsProduced by
PlanOutputcommit_message (for the plan file itself)planner
BuildOutputchanged_files: [], commit_messagebuilder
ScoutOutputfindings: [{file, note}]scout
ReviewOutputapproved: bool, findings: [{requirement, met, evidence}], blocking: []reviewer
DocumentOutputdocument_path, documented_files: [], commit_messagedocumenter
GenericOutput—any (free-form ADW)
VerifyOutputpassed, failures: []code — quality results adapted into envelope shape
ChangesOutputbase, changed_files, stat, diff_path, +/− countscode — git diff capture adapted for the documenter

Adapter trick worth copying

VerifyOutput and ChangesOutput let deterministic code hand results through the same door agents use. A failing test run flows back to the builder exactly like a tester agent's report would — the builder's repair loop cannot tell the difference, so replacing an agent with code (or back) never touches the loop.

Hand-synced, nothing checks it

The JSON example in each role's user.md prompt is hand-written, not generated from the Pydantic model. prompts.render is a plain {{key}} string replace of exactly three variables. If you change an envelope class, you must update its prompt template by hand — consider generating the schema into the prompt in your rebuild.

2.4 Gates: verify claims, never judge quality

A gate is a pure function gate(envelope, run) → GateReport (gates.py). Gates check only what is mechanically decidable; judgement stays with the one reviewer agent.

GateChecks
artifacts_existevery declared artifact path exists under the run's own tree
files_non_emptydeclared artifacts are not zero-byte
json_parsesdeclared JSON artifacts actually parse
diff_matches_claimsevery changed_files entry exists on disk
verdict_consistenta review's approved flag cannot coexist with blocking items or unmet findings
tests_pass(cmd)factory: any shell command, gated on exit 0, cwd = run's tree

2.5 Permissions: enforced after the fact, in code

A tool allowlist cannot express write boundaries (bash reaches everything), so enforcement is a snapshot-diff, not a sandbox (permissions.py). Three mechanisms, all armed per agent phase:

  1. Content diff — fingerprint the tree before, re-fingerprint after; any changed path failing permitted() is rolled back (git checkout -- / delete) and raises PermissionBreach.
  2. Refs tripwire — HEAD sha + branch name snapshotted; any movement (an agent hiding its diff behind a commit/reset/stash) is a breach checked first, with no rollback attempted.
  3. Main-checkout tripwire — once a worktree exists, the operator's own checkout is snapshotted too; an agent reaching into it by absolute path is caught. Protected-path hits are breaches; anything else is traced as drift.

writes: semantics per agent: None = unrestricted (builder only), [] = read-only in the repo, a list = allowlist (trailing / = directory, * = glob). protected_files (the factory's own machinery: adws/adw_modules/, adws/adw_sssf_config/, adws/adw_*.py) blocks every agent that hasn't explicitly named those paths — the factory never builds the factory. A breach is not a gate violation: gates re-prompt, breaches abort the phase.

Known nuance to fix in a rebuild

data_dir (adws/adw_data/) is always writable for every agent — it is the session runtime. But it also holds the checked-in prompt templates and harness extensions, which protected_files does not name. An agent could rewrite its own system prompt and pass enforcement. Carve the templates out of the always-writable set when you rebuild.

2.6 Quality: three states, fail-closed

Deterministic checks return pass | fail | incomplete — never a bare boolean (data_types.py:149). incomplete means the tool never ran (missing toolchain, provisioning failure): it keeps the aggregate red (nothing merges unverified) but is never handed to the builder as something to fix — a repair loop must never receive an unwinnable round. Commands come from the roster's quality: block, one shell string per check with {dev}/{scan} expanding to the pinned-toolchain prefix resolved against the tree being judged:

quality:
  lint:      "{dev} ruff check ."        # or "npm run lint" — any command, any stack
  typecheck: "{dev} mypy adws"           # empty string = check disabled, visibly
  test:      "{dev} pytest -q adws/tests"
  scan:      "{scan} skylos . --ai-defects --format concise"   # AI-defect scan, diff-scoped

The scan runs diff-scoped against the merge-base so a builder is never handed pre-existing repo-wide findings as its own repair spec.

2.7 The trace: SQLite + JSONL, written synchronously

Every event lands in adws/adw_data/sssf.db (WAL mode, busy_timeout 5s, so any UI can poll it live) and as a raw line in events.jsonl. Schema migrations are additive-only ALTER TABLEs from an explicit list.

TableCarries
sessionsone row per run: adw_id (8 hex chars), adw name, request, status, engineer, timestamps, total tokens/cost
phasesphase id/seq/name/kind/owner/description, status, attempt, error, timestamps
eventstyped rows: phase_start | agent_start | tool_call | handoff | gate_pass | gate_fail | log | agent_end | phase_end | error, payload JSON, tokens, spans
envelopesevery parsed envelope, its output type, validity, attempt
gate_resultsper gate per attempt: passed, violations, checks
processespids of the ADW and agent children — ended_at NULL = believed alive (find/kill hung runs)
agent_sessionsper agent per run: harness session id, model, context tokens/window — what makes resume possible

One contract worth preserving: the worktree phase writes a trace event type="log", name="branch" with {branch, path, title} — downstream collectors (the morning brief) query exactly that shape.

2.8 Sessions, resume, and the final verdict

  • session.ensure(cfg, adw_id) mints a fresh id or rejoins a pinned one. Rejoining a session still marked running is refused while its newest event is younger than stale_after_minutes (30) — two processes in one worktree is the one unrecoverable state.
  • SIGTERM/SIGINT converts to a clean session_finish(ok=False) — a killed run never leaves running forever.
  • agent_map.json persists each agent's live harness session id, so a rejoined run continues each agent's context window.
  • run.finish(accepted, reason) settles the verdict in one place: ok = all phases succeeded AND accepted — the ADW's own domain test (suite green, review approved). A phase that ran a red suite still succeeded as a phase. Exit code 0/1; the run's branch is best-effort pushed.
ExceptionMeaning
GateFailuregates still red after retries + 1 attempts (distinct from plain envelope status: fail)
PermissionBreachwrite-scope or refs violation; aborts the phase, never re-prompts
ReconciliationErrortwo branches sharing one adw_id (worktree layer), exit 2
DispatchErrordispatcher refusal, exit 2, card untouched

03The pipelines

Twelve entry-point scripts, one skeleton: load + validate config → session.ensure → request phase → the chain → run.finish(accepted). Loops are plain bounded for loops in Python — there is no framework retry primitive across phases.

Design notes that generalize:

  • Testing is code, never an agent. Running a known command is a code phase over quality.py. There is no tester in the roster at all.
  • Exactly one agent reviewer, narrowed to the one question no predicate can answer: does this do what the ticket asked? Its self-consistency is gate-checked; its verdict is never second-guessed by code.
  • The quality loop breaks early once failures is empty even if incomplete checks remain (an unavailable tool is not fixable by an agent) — but the commit stays gated on the strict verdict.
  • ship_report.py is not an ADW — a pure read-only script that assembles the squash-commit/PR body for everything on integration that main lacks, walking parked cards and answering acceptance checkboxes mechanically (confirmed-by-record / cannot-confirm-from-record), never semantically.

04The model setup

One YAML file is the whole roster: five single-purpose agents, the model each runs on, its thinking level, tool allowlist, and write boundary. Swap the file, swap the factory's brain — no code change.

4.1 The five roles

scoutFind and report where things live; change nothing.[] read-onlymediumsubagent fan-out tools

Each role has a short system.md (identity + standing instructions) and a user.md (task shape + the literal JSON report example), rendered with three variables: {{prompt}}, {{previous_envelope}}, {{context_handoff_dir}}. Identity lives in the config; task shape lives at the call site.

4.2 The config schema

defaults:
  coding_agent: pi              # the harness seam — 'claude_code' accepted by schema, stub only
  model: provider/model-id      # inherited by any agent without its own model:
  thinking: medium              # off | minimal | low | medium | high | xhigh | max
  harness_engineering: []       # harness extensions — MERGES into each agent's list (union)
  tools: [read, bash, edit, write, grep, find, ls]   # allowlist; plain replace per agent
  protected_files: [adws/adw_modules/, adws/adw_sssf_config/, adws/adw_*.py]
  data_dir: adws/adw_data

quality:       { lint: "...", typecheck: "...", test: "...", scan: "..." }
agents:
  - name: planner
    model: ...                  # per-agent override
    writes: [specs/]
    prompt_engineering: { system: .../system.md, user: .../user.md }
    tools: [...]                # an agent naming tools REPLACES the default list wholesale

Two loader rules earned by pain: harness_engineering merges (union, order-stable) so a roster-wide extension never silently vanishes for an agent with its own list; and an extension-registered tool must be named in the agent's tools: list or it loads but gets filtered out. Validation fail-fasts the whole roster before any phase opens: prompt files exist, every model resolves in the harness catalog (a free listing probe, never a generation).

The rules behind the picks — these are the durable part, the models will change:

  • Cross-family review. The family that writes the code never reviews it. Builder is xAI; reviewer is Anthropic. The planner sharing the reviewer's family is fine — the rule binds writer vs. reviewer.
  • No premium models for testing. Smoke tests and lane checks run on the cheap lanes only; the expensive family appears in the shipping roster alone, and even config validation uses a cost-free catalog listing.
  • Context engineering over model choice. “99% of 2026 models can code; the problem is the context you give them.” Effort goes into briefs, pinned skills, and deterministic self-checks — model selection is the operator's alone; agents do no model research.
  • Flat-rate subscriptions only. Zero marginal token spend is a hard constraint: no per-token APIs.

4.4 Lanes: quota, not routing magic

  • A lane has N slots (default 2) = concurrent runs that may draw on it. The engine holds a card rather than dispatching when a needed lane is full.
  • A lane is picked per phase and pinned through that phase's correction rounds — per-call balancing would turn every fix into a cold start.
  • Sub-agent fan-out counts against the parent's lane.
  • Optional router.builder_pool: candidate models for the builder only; the engine picks the lane with most free slots, writes a derived per-run copy of the roster, and dispatches with it. Absent = pinned builder, byte-identical behavior.

Schema subtlety

lanes: and router: are not part of the validated config schema. The engine reads them through its own raw YAML reader, deliberately, so scheduling still answers even when a roster fails agent-validation. One file, two readers, two schemas.

Activation reach

SSSF_CONFIG swaps the roster per run — but it is honored only by just recipes, dispatch.py, and engine.py. Every adw_*.py hardcodes the default path; invoking one directly with only the env var set silently runs the test roster. Pass --config explicitly.

05Queue, dispatcher, engine, worktrees

The operational layer turns a written card into merged code with no human in it until Gate 2. Three pieces, cleanly separated; git itself is the only lock.

5.1 The card contract

A card is one markdown file, queue/NNN-slug.md. Only the header block under the H1 is machine-parsed; the body is the agent's brief, passed through verbatim.

# Title of the change          ← leads the prompt; names the branch slug
Status: ready-for-agent        ← ready-for-agent | running | blocked | done
Adw: simple-sdlc               ← routes to one of the 8 writing ADWs
Adw-Id:                        ← empty until a run claims it; then pinned forever
Created: 2026-08-12
Context:
Needs:                         ← comma-separated card basenames this is blocked on

## Agent Brief
Category / Summary / Current behavior / Desired behavior / Key interfaces /
Acceptance criteria (checkboxes) / Out of scope
— durable, behavioral, written for an agent with no other context.

5.2 dispatch.py — one card, one run

  • A one-shot command, never a daemon. Claims exactly one card, routes Adw: x-y → adws/adw_x_y.py, runs it as a foreground subprocess, writes Status: back twice (claim → terminal). Touches only the Status:/Adw-Id: lines — the body survives byte-for-byte.
  • Refusals (unknown ADW, unmet Needs, already running, read-only ADW) exit 2 with the card untouched. A blocked card retried later reuses its Adw-Id automatically — the run resumes rather than restarting.
  • Invocation contract per run: uv run adws/adw_<name>.py "<title>\n\n<body>" --config <roster> --adw-id <id>, cwd = the main checkout, output streamed with UTF-8 pinned at the pipe. The prompt argument doubles as a file path if one exists on disk.

5.3 engine.py — the always-on loop

  • Caps: --cap (default 2) bounds total live children; per-lane slots bound quota draw. Integration is strictly sequential, oldest first, so each rebase lands on the tip the previous merge created.
  • Blocked is terminal for the loop — a human-shaped problem, taken out of the scan by definition. The reason is written into the card header, committed, pushed, visible.
  • Pull discipline: --ff-only first; on true divergence, replay own commits, dropping only commits whose entire diff is under queue/ — a non-card commit that cannot replay stops the cycle rather than being dropped.
  • Unattended git is hardened at one door (git_helper.py): every git call goes through one runner that disables prompts (GIT_TERMINAL_PROMPT=0, empty askpass, ssh BatchMode), disables signing, and bounds time (300s network / 60s local; timeout returns a failed result, never hangs). One prompt-blocked git call would otherwise stop a single-threaded factory that still looks alive.
  • Environment knobs: SSSF_CONFIG (roster), SSSF_CAP, SSSF_LANES ("xai=2,opencode-go=1"), SSSF_INTEGRATION_BRANCH. main is refused as the integration branch at startup.

5.4 Worktrees: parallelism with git as the mutex

  • Naming: branch adw/<adw_id>_<slug> (slug = first four words of the title); worktree directory = branch name minus the prefix, in a sibling directory outside the repo.
  • Concurrency control is git itself: git worktree add for a branch already checked out elsewhere fails — one branch per run means one tree per run, enforced with no lock file or daemon.
  • Venv isolation: every subprocess pins UV_PROJECT_ENVIRONMENT to the tree's own .venv, provisioned at creation (never mid-phase) — parallel runs never share an environment.
  • Reconciliation (just worktrees): a full outer join of git's worktree list, adw/* refs, and the sessions table, classifying each row alive / orphan / unmerged / merged. Exit 1 means work is stranded — silence is the bug.
  • “Merged” is content equality, not ancestry (git merge-tree output equals the trunk's tree), so squash-merged branches classify correctly. Prune removes only proven-merged rows, with git's own remove/branch -d (never -D) as the second safety net.
  • Escape hatch: worktrees.enabled: false falls back to a branch cut in the main checkout — a written decision for a box that can't support worktrees, never an accident.

06How it sits on a machine

No server assumed. The factory is files in a repo plus a handful of resolved tools; the same product converges on a laptop, a VPS, or a container.

6.1 The deployment unit: stamp, don't install

The factory ships as a skill package whose templates/adws/ is a byte-mirror of the live adws/ tree. A stamper copies it into any target repo under a two-worlds rule:

  • Factory-owned (adws/*.py, adw_modules/, tests, queue/TEMPLATE.md): re-stamped to the package's bytes on every run — a partial refresh once produced a two-generation tree (new engine importing types an old module lacked), so skip-if-exists is banned for these.
  • Operator-owned (the roster YAML, adw_data/, pyproject.toml, justfile, .env, every queue card): never overwritten without --force.

Mirror drift is caught mechanically: a sync-check test runs inside the engine's own merge gate, so an edit to the live tree that skips the mirror goes red on the branch that caused it.

6.2 Execution model

  • Every ADW is a self-contained PEP 723 script (#!/usr/bin/env -S uv run + inline dependency block: pydantic, python-dotenv, pyyaml, rich). uv run uses the script's own metadata and skips the surrounding project entirely — there is no installed package. Don't port it as one.
  • The root pyproject.toml exists for the pinned quality toolchain only: group dev (ruff, mypy, pytest) kept separate from group scan (the AI-defect scanner, whose build needs a compiler on some hosts) so one group's failure never takes the other down.
  • Nothing depends on ambient state: encoding pinned per pipe, extensions loaded explicitly, config paths passed explicitly, launchers (uv, the harness) resolved to absolute paths — bare names on a service's minimal PATH silently failed every dispatched card once.

07The porting map

The factory drives its agents through pi, a coding-agent harness — but the harness is a deliberate seam, one module wide. Everything else is Python + git + SQLite and ports as-is.

7.1 What your harness adapter must provide

  1. Non-interactive invocation with a separate system prompt and user prompt, cwd set to the run's own worktree, stdin closed (an inherited stdin on a non-TTY read hangs forever).
  2. Session continuation. The correction machinery (JSON-fix retries, gate corrections, cross-phase fix loops, resume after a crash) re-prompts the same session so the agent keeps its context. If your harness can't continue a session, every correction becomes a cold start — the loops still work but cost multiplies. A lane that cannot continue cannot sit at a loop node.
  3. Final text returned containing the JSON envelope (the extractor tolerates surrounding prose).
  4. A tool allowlist, or acceptance that the post-hoc permission diff is the real boundary (it already is — the allowlist is intent, the diff is enforcement).
  5. Usage accounting per call (tokens, cost if available) for the trace's per-run totals, and ideally streamed tool-call events for the live trace — both degrade gracefully if absent.
  6. A catalog probe (list models without generating) so roster validation can fail fast at zero cost — or replace with a static check.
  7. Explicit everything: no ambient extension discovery, no config the harness rewrites underneath you as the only home of factory-critical settings.

7.2 What is pi-specific and dies at the seam

  • The subprocess wire format: pi -ne -p --mode json --provider ... --model ... --session-id ... --system-prompt ... [-e ext] and its streamed JSONL event shapes, mirrored by the PiRequest/PiResult/UsageBreakdown types — write your own pair.
  • harness_engineering (TypeScript extension files loaded per agent; the subagent fan-out tools for planner/scout; the claude-bridge extension that puts Anthropic models behind a pi provider). Your harness has its own plugin story, or none — the merge-not-replace loader rule is the part to keep.
  • provider/model naming and the lane vocabulary (ollama-cloud, xai, …) — the lane-per-account scheduling concept ports unchanged; the names are pi's.
  • The Windows landmines (batch-shim truncation forcing PI_PATH, cp1252 encoding pins, timestamp-staleness instead of pid-probing, path-length pressure). A Linux on-prem target sheds most of them — but keep the encoding pin per subprocess and the no-prompt git hardening regardless.

7.3 Suggested rebuild order

  1. The envelope + phase + trace spine (§2.1–2.3, 2.7) with your adapter and one trivial pipeline (adw_prompt-shaped). Prove one verified round trip.
  2. Gates + permissions (§2.4–2.5) — the trust layer. Then adw_build_test-shaped: builder + deterministic test loop.
  3. The roster config + validation (§04) with your model names; wire cross-family review.
  4. Worktrees + dispatch (§5.2, 5.4) — parallelism and the card contract.
  5. The engine (§5.3) last — it only composes what already works, and every piece of it is testable by hand first (dispatch is a command you can run yourself).

08The rules the design lives by

Argued once, then enforced. These explain most “why is it built this way?” questions you'll hit while rebuilding.

  1. KISS. If a ticket's answer is “add a system,” it is probably wrong. A discovered capability is not a reason to add a node.
  2. Validate before running; typed outputs only. No untyped handoffs anywhere — every agent declares a concrete envelope class.
  3. Gates validate claims, not guesses. Deterministic review wherever a predicate can decide; exactly one agent reviewer, never stacked.
  4. Cross-family review. The family that writes the code never reviews it.
  5. One agent, one prompt, one purpose. Identity in system.md, task shape at the call site.
  6. ADW scripts stay thin. All low-level logic lives in the shared modules; a pipeline is a readable sequence of phases.
  7. A known command is code, not an agent. The reason there is no tester role.
  8. Every phase earns a description. Enforced at construction time, before the run is in the trace.
  9. tools: is capability, writes: is the boundary. Enforced in code after every call.
  10. Every ADW ends in run.finish(). One place where phase success meets domain acceptance.
  11. The factory never builds the factory. protected_files covers the machinery, always.
  12. Never depend on ambient state. Explicit paths, explicit extensions, explicit config — per call.
  13. Park, never delete. Uninstall and replace paths move files aside; nothing is ever removed.
  14. Production-grade code, never mock data. The reason the AI-defect scan exists, and why incomplete can never read green.
  15. Two human gates, never in the middle. Mid-run escalation is a defect report against the intake, not a feature.
  16. Trunk-based, with a machine-owned living line. Short-lived adw/* branches into integration; main moves only by the operator's squash. A run either merges or leaves a visible, named artifact explaining why not — silence is the bug.
